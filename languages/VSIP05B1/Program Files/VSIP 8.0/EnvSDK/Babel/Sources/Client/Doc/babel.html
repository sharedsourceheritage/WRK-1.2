Introduction

 This document describes how to integrate programming languages into Visual Studio using the Babel package. The Babel package is available for both the Visual J++ 6.0 environment and Visual Studio 7.0. By a language integration we mean: Syntax highlighting (including customizable color classes); Syntax checking, show red squiglies in the source and show messages in a special task window; Statement completion; Method tips, show the type of the method when providing parameters; Member selection lists; Quick info, show information when hovering the mouse over identifiers; Highlight matching braces; find matching braces; Browsing; Build and deploy management; Project support and Debugger integration. There are basically three ways to integrate a language into Visual Studio:
  • The Visual Studio Integration Partner (VSIP) program. By becoming a member of the VSIP program, you get the VSIP SDK which exposes all the core API's of the Visual Studio environment. Allthough the most flexible and powerful method of integration, it requires a lot of work to integrate a language.
  • The IBabelService interface. The IBabelService interface represents the essential functionality that a language should provide in order to be integrated into Visual Studio. The Babel package provides all the glue code between this interface and the Visual Studio environment. Creating an implementation of the IBabelService is much easier than using the VSIP SDK and might be the right approach if your language compiler is easily adapted to support this interface.
  • The Babel SDK. This SDK implements a default IBabelService interface in C++ which is customized through a lexical and grammar specification of the language. A client only needs to provide these specifications to integrate into Visual Studio. This is by far the easiest way to create a language service and this document describes how to use this approach.
The Babel package supports (automatic) method tips, (automatic) member selection, statement completion, quick info (automatic info when hovering the mouse over an identifier), (automatic) highlight matching brace, find matching brace and block (un)commenting. We hope to extend the Babel package soon with browsing, a build system with automatic dependency analysis, projects and help integration.

Getting started

 Figure [fig:overview] shows how the Babel framework is works. The dynamic link library babelpackage.dll is a Visual Studio package that interfaces between Babel services and Visual Studio. A Babel service is simply a COM component that implements the IBabelService interface and is registered in a special way. This document will explain how to implement such service using the SDK.

Installation

 After installing the Babel SDK, there is a root folder called babel\client. The root folder contains the following sub folders:
  • client\doc. Contains the documentation about Babel, FLEX and BISON.
  • client\tools. Contains FLEX and BISON. Both are free GNU programs. FLEX generates lexical analysers and BISON generates parsers[footnote: The output of both programs is completely free without any licensing issue.].
  • client\common. This folder contains the sources of the common.lib library. This library implements the standard code that implements the IBabelService and interfaces with the generated lexer and parser.
  • client\template. This is the simplest possible language service. This project is used as a template for implementing a language service.
  • client\myc and client\forth. These folders contain examples of a language integrated into Visual Studio using the Babel framework.

Conventions

 The interface to the Babel language package is specified in client\common\babelservice.idl. The code in client\common uses the following conventions:
  • Types and constants start with a Capital letter; class StdService, enum Color { ColorBlack }.
  • Variables start with a lower case letter; token, g_service. Global variables are prefixed with g_ and member variable are prefixed with m_.
  • Argument use is marked as in, out or inout; void increment( inout int* i );. All three identifiers are empty #defines.
  • Methods are marked as final, virtual or override. final is used for a non-virtual method. override is used whenever a virtual method is redefined. Both are empty #defines.

Adding a language

 Adding a language using the Babel SDK is very much an evolutionary process, adding new features one at a time:
  1. Set the language information. This step doesn't add any functionality but enables the integration into Visual Studio.
  2. Syntax highlighting. This is enabled through a lexical specification.
  3. Syntax checking. This is enabled trhough a grammar specification.
  4. Custom colors. Some languages need extended color sets.
  5. Automatic brace matching.
  6. Block commenting.
  7. Statement completion.
  8. Member completion.
  9. Quick info.
  10. Method tips.
The following sections will elaborate on each step. As a running example I will use the MyC language. MyC is an extremely simple C-like language which only uses integers.

Set the language information

 This step installs all the basic machinery needed by a language service.

Create a new project

 First a new project for your language is needed. Luckily, there is a template project with all the boilerplate code and correct settings provided by the SDK. Copy the subfolder client\template to a new subfolder with the name of your language, for example client\myc Click now on the bservice.dsw workspace file in your new subfolder to startup the Visual Studio environment.

Language information

 Open the service.cpp file (in source files). At the top of this file three values need to be supplied that are used during the registration of the package:
  • g_languageCLSID is the CLSID of this specific language. The guidgen utility (which can be run from the start-run menu) is used to generate a fresh CLSID.
  • g_languageName is the human readable name of the language, in our case "MyC".
  • g_languageExtensions are the extensions of the source files ending with a NULL, for MyC this is simply {".myc",NULL}
For the MyC language, the definitions look like: 
  const char*  g_languageName              = "MyC";
  const char*  g_languageFileExtensions[]  = { ".myc", NULL };
  const CLSID  g_languageCLSID = 
     {0x54D21404,0x5E7F,0x11D3,{0xB4,0x07,0x00,0x60,0x08,0xD1,0xBF,0x8C}};
From this moment on it is safe to build the service, allthough no functionality is yet implemented.

Language properties

 The language properties are defined in the g_languageProperties variable. This is an array of LanguageProperty structures. Each property consists of a name and a numeric value. The properties will be put in the registry on registration and determine the behaviour of certain features in the language service. For example, automatic brace matching is only enabled if the property "MatchBraces" is set to one. When no features are implemented yet, the set of properties should probably look like: 
const LanguageProperty g_languageProperties[] =
{
  { "RequestStockColors", 1     },
  { "ShowCompletion",     1     },

  { "CodeSense",          0     },
  { "MaxErrorMessages",   5     },
  { "QuickInfo",          0     },
  { "MatchBraces",        0     },

  { NULL, 0 }
};

Syntax highlighting

 Syntax highlighting is enabled through a lexical specification. The specification consists of regular expressions that recognise the tokens of the language. These tokens are than mapped to color classes which are used by Visual Studio to highlight the source. Implementing syntax highlighting is done in three steps:
  • Define the tokens of the language.
  • Define a mapping from tokens to color classes.
  • Define the lexical specication.

Define the tokens of the language

 Open parser.y (in source files). Language tokens are defined using the %token definitions of BISON. The MyC language contains the following definitions: 
  %token IDENTIFIER NUMBER 
  %token KWIF KWELSE KWWHILE KWFOR KWCONTINUE KWBREAK KWRETURN
  %token KWEXTERN KWSTATIC KWAUTO KWINT KWVOID
  %token ',' ';' '(' ')' '{' '}' '=' 
  %token '+' '-' '*' '/' '!' '&' '|' '^'
  %token EQ NEQ GT GTE LT LTE AMPAMP BARBAR 
  %token LEX_WHITE LEX_COMMENT LEX_LINE_COMMENT
The service should now be build. A file called parser.cpp.h is automatically generated by bison that contains the C definitions of the tokens.

Define a mapping from tokens to color classes

 The tokens in the language should be mapped to a specific color class. For example, the token KWIF should map to the ClassKeyword color class, a NUMBER token to the ClassNumber color class, etc. In service.cpp, this information is provided by the Service::getTokenInfo method. This method returns a pointer to a static TokenInfo array. There is an entry for each defined token. Each TokenInfo structure contains the token, the color class for this token, a description, a character class and sometimes a trigger class. The character classes and trigger classes will be explained later in more detail. Part of the table for the MyC language looks like: 
  static TokenInfo tokenInfoTable[] =
  {
    //TODO: add your own token information here
    { IDENTIFIER, ClassIdentifier,  "identifier '%s'", CharIdentifier },
    { NUMBER,     ClassNumber,      "number ('%s')"  , CharLiteral    },
    { KWIF,       ClassKeyword,     "if"             , CharKeyword },
    { KWELSE,     ClassKeyword,     "else"           , CharKeyword },
    { KWWHILE,    ClassKeyword,     "while"          , CharKeyword }, 
  
    { LEX_WHITE,  ClassText,        "white space"    , CharWhiteSpace },
    { LEX_LINE_COMMENT, ClassComment, "comment"      , CharLineComment },
    { LEX_COMMENT,ClassComment,     "comment"        , CharComment },

    //always end with the 'TokenEnd' token.
    { TokenEnd,     ClassText,      "<unknown>" }
  };
The color classes of MyC are only the default ones. However Babel allows for custom color classes. The default color classes are defined in client\common\babelservice.idl: 
  enum DefaultColorClass
  {
    ClassText,
    ClassKeyword,
    ClassComment,
    ClassIdentifier,
    ClassString,
    ClassNumber
  };

The lexical specification

 Finally, the lexical specification of the language can be added. This specification is used directly by the colorizer to provide syntax high-lighting. The same specification is also used later by the syntax-checker to provide tokens for the grammar. Open the file lexer.lex in source files and add the LEX rules for your language. The document flex.html gives more information on how to specify lexical rules. Most languages already have a LEX specification. If you have one, you can simply copy the rules into the lexer.lex file. However, to meet the requirements of the colorizer, there are some constraints on the form of the LEX rules. To explain the constraints, we will briefly look into the implementation of the colorizer. The colorizer automatically saves the state of the lexer at every line of text. Whenever the line colors could change, the lexer is restarted at this state to colorize this line again. Each time that a token is returned by the lexer, the colorizer will lookup the color class in the table provided by the getTokenInfo method. All the characters scanned for this token are colored with this color class. In order to make this work, the colorizer assumes two things from the lexical specification:
  • The lexer returns a token at the end of a line.
  • No scanned characters are dropped or added during scanning.
The first constraint assures that the lexer is in a known state at the end of the line. The second constraint is needed to determine how many characters are to be colored. The first constraint can be easily satisfied by adding a rule at each lexer state that returns a token on seeing a new-line. For example, many lexical specifications contain the following rule for discarding white space: 
  [ \t\r\n]+    { /* ignore */ }
Since this rule does not directly return a token on a new-line, it should be redefined to: 
  [ \t\r]+    { /* ignore */ }
  \n          { /* ignore */ }
However, now it doesn't satisfy the second constraint since it forgets about the scanned characters. The final and correct definition returns a white space token: 
  [ \t\r]+    { return LEX_WHITE; }
  \n          { return LEX_WHITE; }
Since the token mapping specifies the character class CharWhiteSpace for LEX_WHITE only the colorizer will know about the white space, the parser ignores all white space tokens. (You can change this behaviour by overriding the Service::isGrammarToken method). The second constraint can be enforced in general by always adding an action to a lexical rule (so we don't lose characters) and to allow only three ways to end that action:
  1. return Token;. "I have scanned a token and return its name". This is the normal way of ending an action.
  2. yymore();. "I have scanned something but don't want to return a token yet; continue scanning". yymore() is used here to avoid losing characters in yytext (the currently scanned text) while continuing scanning. It is used in situations like comments where we only want to return the comment token at the end of a comment or line.
  3. yyless(0);. "I have scanned something and changed my state, scan this input again". Here, yyless(0) is used to prevent duplication of characters.
During lexing, there is a global variable g_service available. This variable points to the current language service. The complete interface of a language service can be found in client\common\babelservice.idl and client\common\stdservice.h. Important functions during lexical analysis are:
  • void setLexState( in LexState state);.
    Sets the lexer state. Should be used instead of the FLEX BEGIN macro.
  • void lexicalError( in Severity sev, in const char* msg );.
    Used to send a lexical error. These messages show up at run-time in the task window. Note that this method has only effect during syntax checking and will not work yet during colorizing. An important kind of error is the `hint' which is used to set for example TODO messages in the task list. A hint is given by setting the severity to SevHint. The error message should start with the hint token, not including the comment start. Take a look at MyC for an example.
  • void enterComment(in LexState commentState = 0);.
    If the commentState argument is given, the lexer is put into that state and the current state is saved. Each time this method is called, the comment nesting level is incremented.
  • void leaveComment();.
    Each time this method is called, the comment nesting level is decremented. Whenever it reaches zero, the lexer is put into the state where enterComment was called the first time.
After adding the lexical rules, the colorizer will be working. Open some source files of your language in the Visual Studio environment and enjoy them in multiple colors!

Syntax checking

 Open the file parser.y again and add the grammar rules for the language. The document bison.html contains more information about specifying grammar rules. Most languages already have a YACC compatible grammar. You can simply copy these rules into parser.y. Unlike the lexer, there are no restrictions on the grammar rules. Here are some (simplified) rules for MyC expressions: 
Expr: MulExpr AddOp Expr
    | MulExpr
    ;

AddOp
    : '+' | '-'
    ;


MulExpr
    : PreExpr MulOp MulExpr
    | PreExpr 
    ;

MulOp 
    : '*' | '/'
    ;


Factor
    : IDENTIFIER
    | NUMBER
    | '(' Expr ')'
    ;

Properties

 After having added the language grammar rules, you should set the language property CodeSense to one (in service.cpp) to enable syntax checking. The property CodeSenseDelay specifies the number of milliseconds delay before errors are displayed. In practice a value between 1000 or 2000 milliseconds works well, the default value is 1500. The property CodeSenseFastOnChangeLine should be set to one if errors should be displayed immediately when the user leaves a changed line. This property is enabled by default[footnote: This feature is not supported in the Visual J++ 6.0 environment]. The property MaxErrorMessages gives the maximum number of displayed error messages (per source file). The default value is 5.

Adding error productions

 Now, error productions should be added in order to provide useful feedback to the user. Error productions should be added in such a way that they both provide specific information about the error and, most important, that they allow parsing to recover. The global language service (g_service) can be used to send error messages about errors that are detected during parsing: 
void syntaxError(  in const char*     construct, 
                   in const Location* loc = NULL );

void expectError(  in const char*     construct,
                   in const char*     expecting,
                   in const Location* loc = NULL );

void errorMessage( in Severity        severity,
                   in const char*     message,
                   in const Location* loc = NULL );
syntaxError is used for general errors during parsing. For example, you probably want to add this 'catch all' error production to your grammar: 
SourceFile: Program
          | error     { g_service->syntaxError( "program" ); }
          ;
expectError is used whenever a certain closing token is expected. For example, in the MyC binding there is an error production for catching situations where the closing parenthesis of an expression is absent: 
ParenExpr
    : '(' Expr ')'    
    | '(' Expr error  
              { g_service->expectError( "unmatched parenthesis", ")" ); }
    ;
Sometimes, the location of the error token is not determined by the current point in the input. In that case, the location can be given using the $ notation of BISON which specifies which token determines the position. 
ImportStatement
  : IMPORT QualifiedName SemiColons
  | IMPORT QualifiedName '.' '*' SemiColons
  | IMPORT error SemiColons        
       { g_service->syntaxError( "import  declaration", &$2 ); }
  ;
Putting error productions in the right spot is quite hard, many times error productions add a lot of shift-reduce (not so bad) or reduce-reduce (very bad!) conflicts to the grammar. Try to aim for adding error productions for `common' errors, together with some `catch-all' productions. The MyC sample contains lots of common error productions.

Custom color classes

 For most languages, the default color classes are good enough but some languages have more token categories. For example, Haskell has special color classes for constructors, literate text and non-standard keywords. I will use the client\haskell language as the example for adding custom color classes. First of all, we need to specify that we are going to use custom color classes. Set the language property "RequestStockColors" to zero. Secondly, we will define our custom color classes. Open service.cpp again and add a enumeration definition for your language right after the language information. You should start the enumeration with the last default color class and still use the default color classes where appropiate. The Haskell sample defines: 
enum HaskellColorClass 
{
  ClassPragma      = ClassDefaultLast + 1,

  ClassOperator,
  ClassConsId,
  ClassConsOp,

  ClassSpecialOp,
  ClassReservedOp,

  ClassGreencard,

  ClassLiterateText,
  ClassLiterateStart,

  //some short hands
  ClassSpecial     = ClassSpecialOp,	
  ClassReservedId  = ClassKeyword,
  ClassSpecialId   = ClassKeyword,
  ClassExtensionId = ClassKeyword,	
  ClassCharacter   = ClassString,	
  ClassSelector	   = ClassIdentifier,
  ClassImplicit	   = ClassIdentifier
};
In the token definition array, we can now use the new custom color classes. Here is an excerpt from the Haskell sample: 
override const TokenInfo* Service::getTokenInfo() const
{
  static TokenInfo tokenInfoTable[] =
  {
    ...      
    { VAROP    , ClassOperator	, "operator (%s)",    CharIdentifier },
    { VARID    , ClassIdentifier, "identifier (%s)",  CharIdentifier },
    { CONOP    , ClassConsOp	, "constructor (%s)", CharIdentifier },
    { CONID    , ClassConsId	, "constructor (%s)", CharIdentifier },
    { QVAROP   , ClassOperator	, "operator (%s)",    CharIdentifier },
    { QVARID   , ClassIdentifier, "identifier (%s)",  CharIdentifier },
    { QCONOP   , ClassConsOp	, "constructor (%s)", CharIdentifier },
    { QCONID   , ClassConsId	, "constructor (%s)", CharIdentifier },
    { RECSELID , ClassSelector	, "selector",         CharIdentifier }, 
    { IPVARID  , ClassImplicit	, "implicit parameter", CharIdentifier },
    ...
  };
  return tokenInfoTable;
}
The last step consists of adding default color information for the new custom colors. The method Service::getColorInfo returns a pointer to a static array of color information ColorInfo. Each ColorInfo consists of the color class, its name and a CSS style specification of its appearance. The getColorInfo method should be added right after the custom color class enumeration. The Haskell sample has the following implementation:

Block commenting

Using ctrl-k, ctrl-c or ctrl-k, ctrl-u in Visual Studio 7, you can comment or uncomment selected text. This feature is not supported in the Visual J++ 6.0 environment. To enable block commenting you should implement the Service::getCommentFormat method. First open service.h and add a declaration of the getCommentFormat method: 
class Service : public CommentService
{
protected:
  override const CommentFormat* getCommentFormat() const;
  override const ColorInfo*     getColorInfo()     const;
  override const TokenInfo*     getTokenInfo()     const;
};
The method returns a pointer to a CommentFormat structure which is defined in client\common\stdservice.h: 
struct CommentFormat
{
  const char* lineStart;
  const char* blockStart;
  const char* blockEnd;
  bool        useLineComments; 
};
The lineStart string should be the character sequence that starts line comments, or NULL if not supported. blockStart and blockEnd are the block comment start and end characters. The useLineComments flag should be true if line comment characters are preferred to block comments. This is used when the user selects a block of lines; these can be commented using either line- or block comments. Open service.cpp and implement this method. The MyC implementation is as follows: 
override const CommentFormat* Service::getCommentFormat() const
{
  static CommentFormat commentFormat =  { "//", "/*", "*/", true  };
  return &commentFormat;
}

Automatic brace matching

 When automatic brace matching is enabled, the language service will highlight matching braces whenever the user types them[footnote: This feature is not supported in the Visual J++ 6.0 environment]. The code in the babels service also handles brace `jumping' when the user types ctrl-] in Visual Studio.

Properties

 First of all, the property MatchBraces should be set to one to enable brace matching. When the property ShowMatchingBrace is set to one, Visual Studio will show the line of the matching brace in the status bar; useful when the matching brace is not visible in the view. The property MatchBracesAtCaret determines if the environment will highlight matching braces even when just positioning the caret on a brace, normally it will only highlight when a brace is typed. Be careful before enabling this feature since it might make the user experience of the environment more distracting.

Adding brace match rules

 Next, we are going to add grammar rules to parser.y that specify when matching braces are found. The standard service g_service provides the following methods to signal matching braces: 
void matchPair  ( in const Location& loc1, 
                  in const Location& loc2 ) const;
void matchTriple( in const Location& loc1, 
                  in const Location& loc2, 
                  in const Location& loc3 ) const;
Simple call one of these with the locations of the braces whenever a matching pair (or triple!) is found. Here is for example the code to match parenthesised expressions from the MyC sample: 
ParenExpr
    : '(' Expr ')'   { g_service->matchPair($1,$3); }
    | '(' Expr error 
          { g_service->expectError( "unmatched parenthesis", ")" ); }
    ;
Off course, you should match braces whenever appropiate, also for example when parsing a parameter list: 
ParenParams
    :  '(' ')'            { g_service->matchPair($1,$2); }
    |  '(' Params1 ')'    { g_service->matchPair($1,$3); }
    |  '(' Params1 error  { g_service->expectError( "unmatched parenthesis", ")" ); }
    |  '(' error ')'      { g_service->matchPair($1,$3); 
                            g_service->syntaxError( "parameters", &$2 ); }
Arbitrary ranges of text can be braces. Even triples can be matched as the following code for recognising if-else-then statements from the Forth sample shows: 
IfBlock
  : KWIF IfWordList KWTHEN { g_service->matchPair($1,$3); }
  | KWIF IfWordList KWELSE IfWordList KWTHEN  
                           { g_service->matchTriple($1,$3,$5); }
  | KWIF IfWordList error  { g_service->expectError( "IFBlock", "THEN" ); }
  | KWIF IfWordList KWELSE IfWordList error   
                           { g_service->matchPair($1,$3);
                             g_service->expectError( "IFBlock", "THEN" ); }

Adding triggers

 Due to speed reasons, it is not possible to run the parser on each editor command. In order to recognise matching braces the babel service needs to know when a parse might be needed, ie. when a token is entered that looks like a brace token. The babel service implements this using triggers. Triggers are specified in the Service::getTokenInfo method in the service.cpp file. Open this file and add the trigger TriggerMatchBraces to each token which is (or might be) a brace for your language. Some relevant entries in the MyC sample are: 
override const TokenInfo* Service::getTokenInfo() const
{
  static TokenInfo tokenInfoTable[] =
  {
    //TODO: add your own token information here
    { IDENTIFIER, ClassIdentifier,  "identifier '%s'",  CharIdentifier },
    ...
    { KWVOID, ClassKeyword, "void", CharKeyword   },
    { '(',    ClassText,  "'('"   , CharDelimiter, TriggerMatchBraces }, 
    { ')',    ClassText,  "')'"   , CharDelimiter, TriggerMatchBraces },
    { '{',    ClassText,  "'{'"   , CharDelimiter, TriggerMatchBraces },
    { '}',    ClassText,  "'}'"   , CharDelimiter, TriggerMatchBraces },
    { '.',    ClassText,  "'.'"   , CharDelimiter },
    ...
    //always end with the 'TokenEnd' token.
    { TokenEnd,     ClassText,      "<unknown>"   }
  };

  return tokenInfoTable;
};
The Forth language service will for example add the trigger too for the KWIF, KWTHEN and KWELSE tokens.

Statement completion

 warning: these interfaces might still change

Statement completion shows up in many ways in Visual Studio. The traditional statement completion is invoked whenever you type ctrl-<left arrow> or ctrl-<space>. The environment will complete the current word if possible or show a list possible candidates if there is ambiguity. The key combination ctrl-j always shows the list of identifiers in scope.

Properties

The property ShowCompletion determines if the options show member list and show parameter list are visible in the Visual Studio environment. This property is enabled by default. The property SortMemberList determines if the identifier list is alphabetized. This is enabled by default.

Giving scope information

 In order to do statement completion, information about the declarations and scopes in the source file has to be known to the system. The most general and powerful method to give scope information is by implementing the IScope interface. However, the babel package provides a default implementation that can deal with almost any language is satisfying manner. This document only describes this approach. The standard service g_service has two methods to give scope and declaration information: 
void addScope( in const Location& start, in const Location& end,
               in ScopeKind       kind, 
               in ScopeAccess     access, 
               in ScopeStorage    storage,
               in const Location& name, 
               in const Location& descStart, 
               in const Location& descEnd,
               in const Location* type = NULL,             
               in bool            merge = false 
              );
void addScopeText( in const Location& start, in const Location& end,
                   in ScopeKind     kind, 
                   in ScopeAccess   access, 
                   in ScopeStorage  storage,
                   in const char*   name    = NULL, 
                   in const char*   description = NULL,
                   in const char*   type    = NULL,
                   in const char*   display = NULL, 
                   in bool          merge = false );
The first method takes raw locations for descriptions while the second one takes arbitrary text. The following functions can be used to combine text locations or to get a pointer to the text at a location: 
Location    range( in const Location& loc1, 
                   in const Location& loc2 ) const;
const char* tokenText( in const Location* = NULL, 
                       in const Location* = NULL ) const;
(The pointer returned by tokenText is in static memory). For each declaration and scope, the method addScope (or addScopeText) is called with the start and ending location. These locations give the lexical scope of this declarations. If a declaration doesn't have a lexical scope, like a variable declaration, the locations might simply coincide. The kind determines if this declaration has parameters or if it can contain other scopes; it contains no other semantic information. The kinds are declared in babelservice.idl: 
enum ScopeKind
{
  ScopeUnknown = 0,
  ScopeModule,
  ScopeClass,
  ScopeInterface,
  ScopeUnion,

  ScopeProcedure,
  ScopeVariable,

  ScopeBlock
};
The access determines the visibility of the declaration and its members: 
enum ScopeAccess
{
  AccessPrivate = 0,
  AccessProtected,
  AccessPublic
};
The storage determines, together with the kind, the icon that is displayed for this declaration and it is used to find member information. 
enum ScopeStorage
{
  StorageConstant = 0,
  StorageStatic,
  StorageMember,
  StorageParameter,
  StorageResult,
  StorageLocal,
  StorageType,
  StorageOther
};
The name contains the name of this declaration. The descStart and descEnd parameters contain the start and end location of the declaration. The text between those location is the description of this declaration. The type location contains the type of this declaration. The merge flag should be set to true if the declaration is specified in multiple places and the information should be merged with the previous entries. The rules in parser.y should now be extended with calls to addScope. Let's look at some of the rules in the MyC sample: 
Declaration
  : Type IDENTIFIER ParenParams Block                                                                       
    { g_service->addScope( $1, $4, 
                           ScopeProcedure, AccessPublic, StorageType,
                           $2, $1, $3, &$1 ); } 
  ;
This rule describes a declaration of a public procedure in MyC. The scope of the method extends from the start of Type to the end of Block, ie. $1 to $4. The name is given by IDENTIFIER, ie. $2. The description that should be shown in the quick info, is just the declaration without the block of code, ie. $1 to $3.

By default, the location of a production is the same as that of its first token; each rule contains the implicit assignment: $$ = $0;. Since we want to make sure that the location of Block entails the entire block (and not just the first token {) we need to add some rules to the Block too: 

Block
  : '{' '}'   
      { $$ = g_service->range($1,$2);
        g_service->matchPair($1,$2); 
        g_service->addScopeText( $1, $2, 
                                 ScopeBlock, AccessPublic, StorageOther); 
      }
  | '{' BlockContent1 '}'
      { $$ = g_service->range($1,$3);
        g_service->matchPair($1,$3);
        g_service->addScopeText( $1, $3, 
                                 ScopeBlock, AccessPublic, StorageOther);  
      }
  ;
The first action of the rules is to assign the whole range from begin to end to the location of the Block production. In this particular case it would even be good enough to do $$ = $2 and $$ = $3 respectively but using range is good coding style.

A block itself imposes a lexical scope allthough it has no name or description. Here the method addScopeText is called with the ScopeBlock kind and no text for the name, description or type.

Member completion

Most languages have some kind of modules, classes or structures that have members. These members are normally selected using some kind of operator, like the '.' in Java or the '->' in C++. The grammar rules need to be extended let statement completion work correctly when members are involved. The service has two methods that specify how a member is selected: 
void startSelect( in const Location& name) const;
void addSelect( in const Location& selector, 
                in const Location& name) const;
The grammar should call startSelect whenever a identifier is used in an expression. The method addSelect should be called for every identifier that is selected. For example, a Java grammar should contain the following rules for qualified names: 
QualifiedName
  : IDENTIFIER                    { g_service->startSelect($1); }
  | QualifiedName '.' IDENTIFIER  { g_service->addSelect($2,$3); } 
  | QualifiedName '.' error       { g_service->addSelect($2,$2); 
                                    g_service->expectError( "qualified name","identifier" ); }
The last production with the error is important in practice since this case will occur quite often when the user is typing its source. In the case where the name is completely lacking, the location of the selector should be passed ($2 in the example).

Adding member list triggers

 When typing a selector token, the member selection list should automatically pop up (unless disabled in the option settings of Visual Studio). Again this is implemented by triggers. The trigger TriggerMemberSelect triggers a member completion list. Here is a typical example of such entry in the getTokenInfo method: 
 ...
 { '.',  ClassText,  "'.'", CharDelimiter, TriggerMemberSelect },   
 ...

Quick Info

 Quick info is a feature that will pop up a small text box that describes an identifier when the user hovers the mouse above it. The property QuickInfo should be set to zero to disable quick info. It is enabled by default. Quick info will work when you have member completion implemented. Even when the language doesn't have member selection, you should still call startSelect at every identifier expression.

Method tips

 Method tips are windows with parameter information about the procedure or method that is called. A method tip normally pops up whenever the user types a parameter list token, for example an open parenthesis. It can also be invoked manually by typing ctrl-shift-<space> [footnote: ctrl-shift-I in VJ++ 6.0]. Method tips are automatically supported by Babel when parameter information is added to the parser rules.

Adding parameter information

 The global service has three methods that support parameter information. 
void startParameters( in const Location& ) const;
void parameter(in const Location& ) const;
void endParameters(in const Location& ) const;
The method startParameters is called whenever a parameter list starts with the location of the parameter list start token. parameter is called for every parameter seperator found and endParameters when the parameter list is terminated. Here is a typical example from MyC: 
ParenArguments
    : StartArg EndArg            { g_service->matchPair($1,$2); } 
    | StartArg Arguments1 EndArg { g_service->matchPair($1,$3); }
    | StartArg Arguments1 error  
              { g_service->endParameters(@3);
                g_service->expectError( "unmatched parenthesis", ")" ); }
    ;

StartArg
    : '('     { g_service->startParameters($1); }
    ;

EndArg
    : ')'     { g_service->endParameters($1); }
    ;    

Arguments1
    : Expr ','  { g_service->parameter($2); }  Arguments1
    | Expr
    ;
In MyC, parenthesis enclose a parameter list. The example is complicated by the need to call the different methods exactly at the moment one of those tokens is recognised. In the rule Arguments1 a mid-rule action is needed in order to call parameter at the right moment. Suppose that rule would have been written like this: 
Arguments1
    : Expr ','  Arguments1  { g_service->parameter($2); }  
    | Expr
    ;
In this case parameter will called after the other arguments in the production Arguments1 are recognised. Now all parameter's calls are done in a reverse order! The same kind of problem occura when calling startParameter and endParameter, that is why the StartArg and EndArg productions are explicitly added.

Adding parameter triggers

 Allthough methods tips can now be explicitly invoked, they are much more useful when they pop up automatically when the user opens a parameter list. The triggers TriggerParamStart, TriggerParamEnd and TriggerParamNext trigger a method tip. Simply add the relevant entries to the token info table. The entries for MyC look like: 
   ...
   { '(', ClassText,  "'('", 
          CharDelimiter, TriggerParamStart | TriggerMatchBraces }, 
   { ')', ClassText,  "')'", 
          CharDelimiter, TriggerParamEnd | TriggerMatchBraces   },
   { ',', ClassText,  "','", CharDelimiter, TriggerParamNext    },     
   ...
Not all languages distinguish the parameter list open token from the parameter seperator or closing token. It is always legal to combine triggers. Allthough triggers will trigger a parser action in order to show or dismiss a method tip, the distinction in triggers is only used to optimize some common cases. The parser always has the final decision in showing the appropiate information. For example, in the language Haskell, white space can open a parameter list but also seperates parameters. At the same time there is no specific token for closing a parameter list but a whole set of tokens can close a parameter list. All those tokens should get the TriggerParamEnd trigger while white space gets two triggers: 
  ...
  { LEX_WHITE, ClassText, "white space", 
               CharWhiteSpace, TriggerParamStart | TriggerParamNext },
  ...
In the Haskell case, there is a more serious problem. Since white space now triggers the parameter info, the parser is called on each white space character typed which will degrade the responsiveness of the editor. The solution is to recognise `special' white space that might trigger a method tip in the lexer. In Haskell, that is the first white space after a valid identifier. The following rules in lexer.lex recognise this case: 
<init>{Identifier}    { g_service->setLexState(afterid); 
                        return IDENTIFIER; }

<afterid>{White}      { g_service->setLexState(init);
                        return LEX_SPECIAL_WHITE; }
<afterid>.            { g_service->setLexState(init);
                        yyless(0); }
