Visual Studio .NET Integration Program Readme

This document contains last-minute notes from the Visual Studio .NET VSIP product teams that are intended to help you work around known issues in this release.

1. Visual Studio .NET Integration Program

1.1.Overview

The Microsoft Visual Studio .NET Integration Program (VSIP) provides resources, documentation, and tools you can use to seamlessly integrate your product into the Visual Studio .NET environment. As a VSIP partner, you can take advantage of the latest innovations in Microsoft technologies and programming models. VSIP offers advanced integration scenarios — such as the incorporation of new project systems, new languages, and custom editors — into the Visual Studio .NET programming environment.

VSIP consists of two sets of SDKs, as follows:

  • Visual Studio .NET Integration (VSI) SDK
  • Visual Studio .NET for Applications (VSA) SDK

1.2. System Requirements

The system requirements for VSIP and Visual Studio .NET are the same. VSIP also supports the same platforms as Visual Studio .NET.

For more information, see the Visual Studio .NET documentation and Readme file.

1.3. Installation

Before installing the VSIP Technologies, you must first install the following:

  • A supported operating system
  • Microsoft Visual Studio .NET

To install the VSIP Technologies

  1. Place the VSIP CD in your CD-ROM drive. The autorun sequence should start up.

    If the autorun sequence does not work, run the setup.exe file from the root directory on the CD.

  2. After reading the licensing agreement, choose I Accept and click Continue at the bottom of the page.

1.3.1. Uninstalling VSIP

You can uninstall the SDKs easily using the Add/Remove Programs option provided by Windows.

To uninstall the VSIP Technologies

  1. In the Control Panel, double-click Add/Remove Programs.
  2. In the list of Currently Installed Programs, select Microsoft VSIP Technologies.
  3. Click Remove.

1.3.2. Changing the Default Help Collection

To see the documentation installed with the VSIP Technologies, choose the VSIP collection or the Visual Studio .NET Combined Help Collection from the IDE. The VSIP collection contains only VSIP documentation, while the Visual Studio .NET Combined Help Collection consists of the Visual Studio .NET documentation, the MSDN Library documentation, and the VSIP collection.

Note   To view the VSIP documentation and use context-sensitive Help, choose the combined collection.

To choose the appropriate Help collection

  1. Open Visual Studio .NET.
  2. From the Tools menu, choose Options.

    The Options dialog box opens.

  3. Under Environment, choose Help.
  4. From the Preferred Collection drop-down list, choose VSIP or Visual Studio .NET Combined Help Collection, and then click OK.
  5. Close the IDE, and then reopen it.
  6. From the Help menu, choose Contents.

    The Contents window opens and displays the specified table of contents.

1.4.1. Visual Studio .NET Environment SDK

The following are known issues associated with the Visual Studio .NET Environment SDK:

  • If you are using Visual Studio .NET as your development environment, you might experience some exceptions when debugging Visual Studio. In the debug output, you might see several instances of the following message:

    First-chance exception in devenv.exe (MSO.DLL): 0xC0000005: Access Violation.

    To avoid seeing this message:

    1. Click Exceptions on the Debug menu.
    2. Select "c0000005 Access violation" in the Win32 Exceptions section of the Exceptions dialog box.
    3. Make sure that the action under When the exception is thrown is set to Continue.
  • Your existing VSPackage will not load in a new build of Visual Studio .NET if you do not rebuild it with the current headers and .lib files provided with the VSIP SDKs.
  • The EnvSDKBase.txt file that appears in the [drive:][path]\VSIP\EnvSDK\ directory contains information about .dll base addresses for all of the samples. It is specified for use by the linker in the .vcproj files, through the /BASE:@envsdkbase.txt;<dllname> option. The base address of a .dll file can also be stated explicitly, using the option /BASE:0x50000000. The hex number represents the actual base address.

    To get the best performance for your VSPackages, you should avoid loading your VSPackages within the following address spaces, which are used by Visual Studio .NET: 

    0x30B00000 to 0x31449FFF
0x4f000000 to 0x5fffffff
  • When developing and shipping your VSPackages, be aware that if a user logs onto a machine as a guest, no third-party VSPackages load. This is not a failure of the Visual Studio .NET code, but rather an express design of the security mechanism of the CryptoAPI.
  • When building any sample on Windows NT 4.0, you receive an error such as the following:

    Error PRJ0002: error result returned from 'D:\TEMP\BAT00000D.bat.'

    The error occurs during registration. This error is invalid and your sample project will work as designed.

  • After building the Figures sample and adding a new Figures project to a solution, "Circle", "Arrow", and "Rectangle" appear in the toolbox. Dynamic Help will not display specific information for any of these three items. However, "Rectangle" information from the Platform SDK is displayed in the Dynamic Help window. This is typical behavior as a result of the extensibility of keywords within the Help system.
  • If your VSPackage provides any objects that extend the Visual Studio automation model, then you must create runtime callable wrapper assemblies for your objects and place the assemblies in the Microsoft Visual Studio .NET\Common7\IDE\PublicAssemblies directory of the machine on which your VSPackage is installed. Without proper assemblies in this directory, your automation objects will not be available to the VSMacros IDE. For more information, see "Advanced COM Interop" in the .NET Framework SDK.
  • If your setup runs custom actions (such as, devenv.exe /setup) you should include the msidbCustomActionTypeContinue type in the CustomAction table of your MSI. If you do not include this type, your uninstall might roll back if Visual Studio .NET is uninstalled prior to your product being uninstalled. For more information, see the Custom Action Return Processing Options topic in the Windows Installer 2.0 SDK.
  • The documentation for the IVsTextManager:EnumViews method is incorrect. Do not pass a value of NULL in the pBuffer parameter to return all views for all buffers. This will cause Visual Studio to crash.
  • When naming a satellite .dll for your VSPackage, use a unique name that is different than the name of any Visual Studio satellite .dll. If you use a name that is not unique, the Visual Studio .dll files will fail to load. To determine the names of the Visual Studio satellite .dll files, search for *.dll in the <drive>\Program Files\Microsoft Visual Studio .NET folder. Do not use the name of any .dll file found in a \1033 folder.

1.4.2. Microsoft Help 2.0 SDK

The following are known issues associated with the Microsoft Help 2.0 SDK:

  • Help collections without merged query (.HxQ) files must be installed on the user's machine.

    If a Help collection does not use .HxQ files and is installed to run from a CD, any search will return zero hits after an Advanced Media Support (AMS, a CD-swapping dialog box) request until the Help collection is restarted.

    Resolution: Design small documentation sets to always install content to the user's hard drive. Design large documentation sets that require a run-from-source option to use .HxQ files.

1.4.3. Microsoft Help Authoring Guide

There are no known issues.

1.4.4. Microsoft Help Integration Guide

  • Administrator privileges are required when end users are plugging a complied help (.HxS) file into the Visual Studio Combined Collection (VSCC) on NTFS computers

    On computers formatted using NTFS, end users must have administrator privileges to plug Help collections in to the VSCC. This behavior is by design. Your setup should not allow the plug-in registration unless it is installed under administrator privileges.

  • Add VIntegration_VS7_RTL_---_---.msm and VIntegration_VS7_AppSearch_RTL_---_---.msm to installation packages.

    If Visual Studio .NET is not installed to the default location, the Visual Studio documentation cannot be viewed after installing a VSIP partner product. If a VSIP partner product integrates documentation with the Visual Studio .NET Combined Help Collection, the Visual Studio .NET Combined Collection files are installed and registered to the default location, thus breaking the MSDN plug-in.

    Workaround: Consume VIntegration_VS7_RTL_---_---.msm and VIntegration_VS7_AppSearch_RTL_---_---.msm in your setup. By default, the .msm files are installed to the \Program Files\VSIP\Deployment\Redistributable MSMs directory. These .msm files ensure that the Visual Studio .NET Combined Help Collection files are installed to the same location as the current version of Visual Studio on the machine.

The Visual Studio for Applications (VSA) SDK provides source code, resource files, samples, and documentation that you can use to integrate VSA technology into host applications.

The VSA SDK includes the following:

2.1.3. Redistributable Files

The VSA SDK includes a library of redistributable files that allow you to deploy your VSA-enabled application with a full complement of both runtime and design-time components. The VSA redistributable files will be translated into the eight natural languages that VSA supports.

The complete list of files and components is provided with the VSA SDK Redistributables CD, which is available only through the VSIP program. For more information, see http://msdn.microsoft.com/vstudio/vsip/ or http://vsip.summsoft.com/.

The VSA SDK Redistributables CD contains a Readme file that provides extensive information, including a catalog of redistributable files, descriptions of their supported scenarios, and instructions for deploying the redistributable files.

The system requirements for VSA SDK are the same as for Visual Studio .NET.

2.5. Known Issues

  • You should not use the IVsaEngine.Evidence property to change the permission set granted to an assembly. By default, customization code runs in the security context of the host, which must be set to Full Trust. Reducing this permission level using the Evidence property will cause the script engine to fail at runtime.

    In future releases of the .NET Framework, the IVsaEngine.Evidence property will allow hosts to run customization code under a more restrictive permission set. In the present release, however, both the host and the customization code must run with Full Trust, which is the default for locally executing programs.

    Because customization code must run with Full Trust, you should never run script code from untrusted sources, such as the Internet. Only code that has been written or reviewed by trusted employees should be allowed to execute inside a VSA host application.

    Resolution: Not applicable.

  • Global function in JScript .NET can only be called internally by the JScript .NET script engine.

    The JScript language allows users to write global functions, and the JScript .NET script engine provided with VSA fully supports this feature. Nevertheless, these functions have special signatures and can only be called internally by the JScript engine. VSA hosts should not attempt to use Reflection to extract and call global functions from a JScript assembly. A host should only use Reflection to retrieve and call functions that are declared inside classes, which are also known as methods.

    Resolution: Not applicable.

  • When running the West Coast HelpDesk sample on your local machine, but with the SQL Server database located on a remote computer, both the Windows and Web clients will fail to connect to the database. The problem occurs because there is no user account with adequate permissions on the remote computer.

    Resolution: Resolving this problem requires you to modify the Web client, Windows client, Workbench, and code provider source file, as shown in the following procedures.

    • Web Client
    1. On the remote machine, set up the SQL Server database using the SQL scripts installed with the VSA SDK on your local machine.
    2. On the remote, create a new user Login.
    3. Add this new user Login to each database that you created with the SQL scripts, granting read/write access to the West Coast HelpDesk database and read/write and execute permissions to the VSACustomization database.
    4. Open the Web.config file for West Coast HelpDesk on the local machine from the path <drive>:\Program Files\VSIP\Visual Studio for Applications SDK\Samples\wwwroot\WestCoastHelpDesk\.
    5. In the web.config file, change the values for the dsn key to include the following: User ID=<new user account>; password=<new user account password>; server=<machine name of remote computer>, where "new user Login" is the one you created in previous steps.
    6. In the Web.config file, remove the Trusted_connection=true key; next, replace server=localhost with server=<database name>.
    7. In the Web.config file, change the following:

      <add key="moniker" value="Fabrikam://WestCoastHelpDesk/localhost/mycustomer/VSACustomizations/Incident"/>

      -to–

      <add key="moniker" value="Fabrikam://WestCoastHelpDesk/<machine name>/mycustomer/VSACustomizations/Incident"/>.

    8. Save and close the Web.config file.
    • Windows Client
    1. Locate the Fabrikam.WestCoastHelpDesk.WinClient.exe.config file at the path <drive>:\Program Files\VSIP\Visual Studio for Applications SDK\Samples\WestCoastHelpDesk\WinClient\WinClientUI\Bin\Release
    2. In Fabrikam.WestCoastHelpDesk.WinClient.exe.config, change the moniker key such that moniker reference is to the machine on which the database is installed rather than to localhost, as follows:

      Fabrikam://WestCoastHelpDesk/<machine name>/mycustomer/VSACustomizations/WorkItem

      where <machine name> is the name of the remote computer on which the database is running.

    • Workbench
    1. Locate the WestCoastHelpDesk.wct file at the path <drive>:\Program Files\VSIP\Visual Studio for Applications SDK\Samples\Workbench\.
    2. In the WestCoastHelpDesk.wct file, change the monikers for both the Incident and WorkItem customizations such that their monikers refer to the remote machine on which the database is running rather than localhost, as follows:

      Fabrikam://WestCoastHelpDesk/<machine name>/mycustomer/VSACustomizations/Incident

      -and-

      Fabrikam://WestCoastHelpDesk/<machine name>/mycustomer/VSACustomizations/WorkItem

      where <machine name> is the name of the remote computer on which the database is running.

    • Code provider source file

      The following steps are required for the Workbench to work, and to run the VSA customization in either the Web or Windows clients.

    1. Locate the SQLCodeProvider.cs file at the path <drive>:\Program Files\VSIP\Visual Studio for Applications SDK\Samples\WestCoastHelpDesk\SQLCodeProvider
    2. In SQLCodeProvider.cs, in the BuildConnectionString method, remove the Trusted_Connection key from the connection string.
    3. Also in the BuildConnectionString method, add User ID=<login name> and password=<password>, where <login name> and <password> are those provided when you created the user account with read/write and execute permissions for the VSACustomization database in step (c) of the Web Client section, above.
    4. Build the WestCoastHelpDesk solution.
    5. Copy the newly compiled Fabrikam.WestCoastHelpDesk.SQLCodeProvider.dll from the WestCoastHelpDesk\SQLCodeProvider\Bin\<Release/Debug> folder into the wwwroot\webcodeprovider\Bin folder.
  • While the VSA runtime is thread-neutral, the VSA design time can be hosted only in a single-threaded apartment. As a result there is no guarantee that the VSA design time will work properly if hosted in any other type of threaded environment.

    Resolution: Not applicable.

  • Before compiling source files provided with the VSA SDK that you have modified, you must change the namespace for that code file to avoid overwriting the original assemblies. You must also change the name of the output DLL.

    The VSA SDK provides source files for the Microsoft.Vsa.Hosting.dll and Microsoft.Vsa.Hosting.Designtime.dll assemblies, which you can open, edit, and build. However, if you do not change the namespace of these components before you compile them, the rebuilt files will overwrite the original DLLs provided with the SDK.

    Resolution: Change the namespace for SDK components that you modify prior to compiling them, and also change the name of the output DLL. Before changing the original source files, you should copy them to a new directory.

  • Calling the LoadEngineSource method on the DesignTime class with the moniker argument set to NULL, that is, with no customization specified, makes it impossible to create a new engine.

    Resolution: Always call the LoadEngineSource method with a valid moniker.

  • Modifying pre-generated code that is marked in the editor "Automatically generated code, do not modify" could result in end users getting an error reading "Check IDE for errors"; however, the error dialog box appears behind the VSA IDE and may go undetected by the user. Examples of occurrences that may cause this error include the following:
    • The user changes the constructor of the opportunity_Customization class to be private rather than public.
    • The user changes the constructor signature to include an additional parameter.
    • The user renames the class that exposes customization events.

    Resolution: Users should not modify pre-generated code.

  • The VSA SDK installation appears to hang during the period when it shows a dialog box that reads "Removing Backup Files." At this point, the installation pauses for some minutes while updating the full set of Visual Studio.NET Help files, which are extensive. While it may seem that the install has hung, in fact it has not.

    Resolution: Not applicable.

  • Code developed using the VSA SDK Beta 2 release must be recompiled using the current version of the VSA SDK. Additionally, changes to VSA code require that you remove HTTP handlers if you use a Web.Config file, and that you set the IVsaEngine.RootNamespace property for your runtime script engine.

    Resolution: Recompile all customization code using the current version of the VSA SDK. Set the RootNamespace property for your runtime script engine. Remove HTTP handlers from your Web.Config file, if applicable.

  • You must be logged on with an account that has Administrator privileges to run the VSA SDK samples.

    Resolution: Log on with an account that has Administrator privileges.

  • An error in the Help system causes VSA SDK documentation to not be visible if you set it as the preferred collection.

    Resolution: You can correct this problem by editing the filter.

    1. From the Help menu, select Edit Filters.
    2. In the resulting window, select Visual Studio for Applications. The filter is displayed with the following values set: DocSet="VSM" or DocSet="URTFramework".
    3. Change the filter values as follows: DocSet="VSA SDK" or DocSet="VSIPSDK".
    4. Save the filter.

    You can now select the VSA SDK as your preferred Help collection.

Product changes or errors detected after completion of VSA SDK documentation have resulted in incorrect information persisting in the documentation. Following are known instances of incorrect information in the VSA SDK documentation:

  • In the topic "Sample Walkthrough," in the West Coast Sales sample abstract, the procedure "To edit the Sales_Opportunity MTO" includes an incorrect file path for accessing the WestCoastSales.wct configuration file. The correct path follows:
